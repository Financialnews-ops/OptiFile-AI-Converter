# Changes — OptiFile AI Converter

Six fixes applied. All changes verified against TypeScript, full Vite build,
and a smoke test on a real Polish PDF.

## 1. Bug fix — DOCX → HTML lost paragraph breaks

**File:** `src/lib/converter.ts`

The regex `/\\n/g` was matching the literal two-character sequence
`\` + `n`, not actual newlines. As a result, DOCX-to-HTML output was
a single un-broken paragraph.

**Fix:** changed to `/\n/g`.

## 2. Security — API key was leaking into the client bundle

**File:** `vite.config.ts`

The `define` block:
```ts
'process.env.GEMINI_API_KEY': JSON.stringify(env.GEMINI_API_KEY)
```
inlined the deployer's environment key into the JS bundle at build time.
Anyone viewing page source on a deployed instance could extract it.

**Fix:** removed the `define` entirely. The app is BYOK (bring-your-own-key)
by design — `src/lib/converter.ts` was also updated to drop its
`process.env.GEMINI_API_KEY` fallback. The user-supplied key (Settings
drawer → localStorage / sessionStorage) remains the only source of credentials.

## 3. Optimization — local PDF extraction as a fast path

**Files:** `src/lib/converter.ts`, `package.json`

Previously every PDF (including text-based ones generated by Word, LaTeX,
etc.) was sent to Gemini vision. That contradicts the app's value
proposition — converting to save tokens — by burning Gemini tokens during
the conversion itself.

**Fix:** added `pdfjs-dist@^4.7.76` and a new `extractTextFromPDFLocally()`
helper. The flow is now:

1. Try local extraction with `pdf.js`.
2. If it returns meaningful text → return immediately, zero API cost.
3. If it returns null (no extractable text on any page, or implausibly
   little for the file size) → fall through to the existing Gemini
   vision path. This handles scanned PDFs correctly.

Smoke-tested on the project's `poniedzialek_05_05_carousel.pdf` (6 pages):
local extraction gave 837 tokens of clean text in <1 second; the same
file through Gemini vision would have been ~6,000 tokens. **~86%
saving** on a real document, with Polish diacritics preserved exactly.

## 4. Quality — language preservation in Gemini prompts

**File:** `src/lib/converter.ts`

All four prompt variants (JSON / HTML / image-OCR / generic) now start
with a `LANGUAGE_DIRECTIVE` block that:

- instructs Gemini to detect the source language and produce output
  in the *same* language (no translation),
- explicitly lists Polish, German, and similar diacritics as
  characters to preserve byte-for-byte.

This addresses the well-known Gemini-vision drift toward English
translation on non-English source documents.

## 5. (skipped — see #5 in the original plan)

Backend proxy for Gemini was deliberately not implemented. It would
conflict with the BYOK + "processed locally or securely via Gemini API"
positioning, add latency, and shift cost responsibility onto the
deployer. It remains a future option if the app pivots to a managed
service.

## 6. UI — Format Guide rebrand + token counter

**Files:** `src/App.tsx`, `src/components/ConversionResult.tsx`,
`src/lib/tokens.ts` (new)

### Format Guide rebrand

The "Premium" tags on JSON and HTML were inverted relative to the app's
own value proposition (HTML is the *most* token-expensive format, not
the most desirable). New labels:

| Format | Old tag | New tag | Reason |
|--------|---------|---------|--------|
| TXT | (none) | (none) | Universal fallback. |
| MD | (none) | **Best for LLMs** (emerald) | Lowest token footprint. The default for AI workflows. |
| JSON | Premium | **Developer / API** (cyan) | Honest category — structured-data target. |
| HTML | Premium | **Browser-ready** (blue) | Honest category — for rendering, not LLMs. Description now warns about token weight. |

### Token counter (signature feature)

New `src/lib/tokens.ts` module wraps `gpt-tokenizer` (cl100k_base, GPT-4
reference). After a conversion completes, the result panel now shows:

- per-file: estimated output token count, plus a `-NN%` chip when the
  saving vs raw input is meaningful (≥5%);
- total summary: combined output tokens, plus combined savings vs the
  estimated raw-input cost.

cl100k_base is used as a cross-model reference (Anthropic and Gemini
tokenizers differ from it by roughly ±10% on typical prose, with the
same directional behaviour). The footnote in the UI is honest about
this limitation.

`gpt-tokenizer@^2.5.0` was added — pure JS, ~80 KB gzipped, no WASM,
runs in the browser without a worker.

## Verification done

- `npx tsc --noEmit` → no errors.
- `npx vite build` → succeeds, bundles `pdf.worker.min.mjs` correctly.
- Node smoke test on a real Polish PDF → all assertions pass:
  - Polish: 20 tokens, English: 8 tokens (matches earlier measurements).
  - 6-page PDF extracted to 2,112 chars in <1s.
  - All Polish diacritics preserved.

## Bundle size note

The build emits a warning about chunk size (~2.8 MB main bundle,
gzip ~970 KB). This is expected — pdfjs, mammoth, xlsx, JSZip, the
Gemini SDK, and the new tokenizer add up. If startup time becomes a
concern later, the natural next step is dynamic `import()` for the
heavy converters so the bundle is split per-format, but that is a
separate refactor and was not in scope here.
